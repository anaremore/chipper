# UI Architecture

Chipper should feel like one instrument with many chip profiles, not a bundle of unrelated mini-plugins. The UI is therefore data-driven: the outer workflow stays stable while each chip definition decides which controls appear inside each module.

Planning sync: this document reflects the current July 2026 direction. FM held-note fade-out and NES DMC loop-off playback are treated as fixed regressions covered by tests and release gates, not active design questions. The editor is one coherent chip surface; the preset browser is the only separate task surface.

## Chipper JUCE UI Working Rules

Use these rules whenever editing the JUCE plugin editor, LookAndFeel, custom controls, parameter attachments, chip-specific panels, or descriptor-driven UI metadata. Generic frontend/design guidance can inspire hierarchy and spacing, but Chipper UI decisions must stay grounded in JUCE, APVTS, host automation, and chip-native behavior.

- Keep `PluginEditor` thin. Prefer reusable components, layout helpers, and descriptor metadata when a pattern repeats across chips.
- Use APVTS attachments for parameter binding. UI code must not mutate DSP state directly or bypass host automation/MIDI mapping.
- Keep `paint()` cheap: no file IO, sample loading, parsing, allocation-heavy analysis, or expensive per-frame work.
- Use chip-accurate controls. Hardware choices should be segmented or stepped; continuous sliders belong only on continuous behavior or deliberate macro layers that clearly resolve to chip-native values.
- Preserve readability over decorative retro styling. A themed control that clips text, hides a level lane, or forces tiny hit targets is a regression.
- Support HiDPI and the current fixed editor sizes. If a chip needs more room, rebalance the chip layout or create a deliberate chip-specific aspect/secondary view instead of shrinking standard controls.
- Keep visual theming tokenized by chip so color/style changes do not fork layout logic or obscure shared component behavior.

Chip-specific anchors:

- NES/RP2A03 exposes five visible channels: Pulse 1, Pulse 2, Triangle, Noise, and DMC. Pulse duty belongs under the pulse voices, noise mode/period belongs under Noise, and DMC uses its native DAC/rate/file-bank controls rather than a fake oscillator or conventional level trim.
- SID sync, ring, model, combined waveform bits, and filter routing should be explicit. Cutoff and resonance stay with the filter.
- Game Boy/DMG pulse duty is independent per pulse channel; Pulse 1 owns NR10 sweep, Wave owns its 32-sample RAM shape and NR32 level, and Noise owns its NR43 width/clock controls. The current engine exposes one pulse initial-level helper and one shared envelope-decay helper for Pulse 1, Pulse 2, and Noise, so those controls live in an explicitly shared `Pulse + Noise Envelopes` module rather than being falsely duplicated per lane. Chip Poly allocates pitched notes only across Pulse 1, Pulse 2, and Wave; Noise remains an SFX lane.
- SN76489 uses an intentionally asymmetric channel deck: Tone 1–3 are compact square-wave cards, while Noise is deeper because it owns feedback mode/rate, preset-only register bias, native attenuation, and a separate modern trim. Tone Stack and Pitch Motion sit directly beneath the three tone cards because they affect that group, not Noise. Tone 3's possible noise-clock relationship stays visible in its card label, and Chip Poly allocates only the three tone lanes.
- YM2612/Genesis FM, YM2151/OPM, OPL, and OPLL surfaces should expose operator, algorithm, envelope, feedback, rhythm, DAC, and pan concepts instead of pretending FM is a simple subtractive synth.
- Sampler and wavetable chips should put per-channel sample/wave selection plus level in the source card. Shared banks, loops, echo, routing, filters, and output live in shared modules.

UI review checklist:

- Is any control confusing, mislabeled, or placed away from the chip block it controls?
- Is any fake-continuous slider really a register choice that should be segmented or stepped?
- Are standard-height dropdowns, buttons, text boxes, and level lanes visible and readable?
- Is retro styling harming usability, contrast, or hit targets?
- Is there a concrete reusable `Component`, layout helper, descriptor field, or LookAndFeel token that would reduce repeated layout risk?

## Execution Contracts

Use these contracts when deciding whether a UI change is ready to ship:

- Chip-owned controls live with the source that owns them. Pulse duty belongs under pulse channels, noise mode/period belongs under noise channels, wave/sample selection belongs under wavetable or sampler voices, and native level trims stay visible inside each card.
- Shared modules are for truly shared behavior: filter, echo, sample bank, output, routing, pairing, global clock/strictness, and performance helpers. Do not move a channel-local control into a generic helper panel just to save space.
- Standard-height dropdowns, buttons, numeric inputs, and visible level rows are non-negotiable. If a chip needs more room, grow the layout or use a chip-specific fixed aspect ratio instead of shrinking controls until text or sliders disappear.
- Roadmap controls stay in docs until they have engine behavior, stable APVTS identity, MIDI mapping, preset recall, and renderer or descriptor coverage. Once a bug has a passing release gate, keep it out of active UI planning unless a current build reproduces it.
- Strictness is a behavior request. Verification status remains an evidence label in the footer/docs and must not imply hardware or cycle accuracy without tests.

Descriptor smoke tests are the fast guardrail for source-card ownership and truthful helper-envelope wording. When a visible source-card control is added or moved, update `ControlSurface::sourceCards`, APVTS/CC mapping, presets, renderer/debug metadata, and tests together. When a chip lacks native ADSR, its module copy must stay explicit about Chipper amp/gate helpers rather than borrowing NES decay or synth ADSR language.

YM2612/OPN2 and YM2151/OPM now have four stable FM Operator Level trims in APVTS, MIDI CC, preset metadata, renderer flags, descriptor metadata, debug JSON, and the Operator EG surface. Both modes also use the stable CC93/APVTS slot as chip-aware native LFO Depth: OPN2 reports `$22` rate plus `$B4` AMS/PMS bits, while OPM reports `$18/$19/$1B` depth and `$38+n` sensitivity. The compact row UI pairs each carrier/modulator lane with its percent trim slider and resolved total-level readout without inventing unbacked FM controls.

## Stable Shell

Every chip mode uses the same outer workflow, but the visible sections are unnumbered and may expand, merge, or hide according to the selected chip. The stable shell is:

- Header: ASCII logo, preset browser, Load/Save/Save As, Chip Mode, Strictness, and Note Allocation (the stable host parameter remains `Play Mode`).
- Chip summary: one short truthful sentence about the selected chip model and implementation status.
- Unified chip surface: the complete active signal path, including native channels, operators, sample voices, wavetable lanes, channel-owned controls, shared shaping, routing, and assets.
- Shared performance and output strip: only genuinely cross-channel helpers, note-allocation context, output trim/scope, MIDI/build/status badges, and compact verification text.
- Preset browser overlay: search, role filtering, chip-family navigation, favorites, history, user banks, and explicit sound loading.

Play/Edit/Info navigation is intentionally absent. Those tabs split one instrument into administrative destinations and obscured relationships between source, shaping, helper, and output state. Progressive disclosure happens inside the unified surface through layout, emphasis, chip-specific density, tooltips, and bounded detail components; it never requires leaving the instrument.

`Source/UI/ChipUiModel.*` is the shared presentation policy for all chip modes. It classifies each chip into a reusable editing family and browser group, owns source-density policy, and centralizes the editor-height policy. Chip descriptors remain authoritative for parameter labels, help, implementation status, and source counts; the UI model translates those facts into layout decisions without duplicating audio or parameter state.

The whole chip remains visible. Selection or density policy may increase one channel's visual weight, but other channels retain identity, enable/activity, and mix state. Native controls live with their hardware owner; shared Chipper helpers stay in the shared performance strip and are labeled as helpers. Authenticity is contextual: short verification status stays in the summary/footer, while detailed evidence and known gaps remain available in tooltips, descriptor exports, and documentation rather than a separate Info destination.

The footer/status area should include a subtle generated build label so a tester can match an installed VST3 to the reported source revision. It should also show a compact MIDI CC range badge with a tooltip for the full fixed hardware-control map, keeping MIDI discoverability close to the build/status information without crowding chip controls. Long accuracy caveats belong in tooltips or docs; the visible footer text should stay short enough that build and MIDI badges never cover it.

The compact header keeps one current-preset chooser plus a `Browse` action. Search, role filtering, chip-family navigation, user-bank discovery, favorites, history, and descriptive preset detail live in the dedicated `ChipperPresetBrowser` surface instead of competing for header width. The browser reads the full factory catalog and recursively indexes portable `.chipperpreset` files, can load a sound from another chip explicitly, and records only explicit user selections as recent history. Favorites and recent keys are UI-library metadata outside APVTS, so presets and host projects do not carry personal browser state.

The summary row also owns a stable `ChipperWorkflowBar`. Visual separators group history, A/B audition, clipboard, and creation actions so the eight controls do not read as one undifferentiated button row. Undo and Redo use the processor's APVTS `UndoManager`, while Paste, section initialization, and safe variation are each grouped into one host-visible transaction. A/B slots are kept independently per chip so switching hardware families cannot restore stale parameter state. Copy/Paste captures a whole automatable sound but refuses cross-chip paste; safe variation is narrower by design and touches only musical macros plus enabled native-source levels, never chip mode, Strictness, clock, routing, sample assets, or native register choices. Sources, Musical controls, Output, and Whole chip initialization are explicit menu choices rather than one destructive reset with unclear scope.

Keyboard focus uses one editor-level `ChipperFocusOutline`, keeping a consistent high-contrast ring around header, workflow, browser, and nested family controls without requiring every component to implement custom focus painting. The browser, workflow buttons, header Browse action, and chip controls receive descriptive accessible names and logical focus order. Zero-size or hidden controls are removed from keyboard focus during refresh. Ctrl/Cmd+B opens the browser, Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z undo/redo, Ctrl/Cmd+F focuses browser search, Enter loads the selected browser result, and Escape closes the browser. Ctrl/Cmd+1 through +3 are deliberately unassigned.

The editor preserves a per-chip working snapshot when users switch chip modes. Shared APVTS parameters are reused across chips, but the UI stores each chip's current preset selection, user preset source, and exposed control values before switching away, then restores them when the user returns. This lets users compare NES, SID, SNES, FM, and sampler ideas without losing the sound they were shaping on each chip.

The module contents may change, but the mental model should not. Users should learn where concepts live once and carry that knowledge across NES, DMG, SID, YM2149, SN76489, POKEY, FM, wavetable, and sampler-style modes. Section headers are unnumbered so chip-specific layouts can hide, merge, or expand conceptual zones without implying that panels are missing.

HuC6280, Namco WSG, and SCC expose independent wavetable voices. Their UIs present per-channel or per-lane wave choices rather than a single global wave-shape switch; Chipper reuses stable automatable choice slots in those modes so MIDI/host control can address each channel while the engine seeds each channel's own Wave RAM. HuC6280 has a six-card template for its LFO/noise roles. Namco WSG has a dedicated eight-lane, four-column bank at a compact 720 px height. SCC has a dedicated five-channel 3+2 bank at 720 px; channels 4-5 are centered beneath 1-3 so the surface reads as an intentional five-voice instrument. It also states the current topology explicitly: emu2212 enhanced mode provides five independent 32-byte waves, while original-SCC channel 4/5 sharing is not modeled. The cores must seed each lane from its own selector, not merely report independent choices in metadata. Every card reserves a standard selector plus a visible source-level lane.

Source-card controls should read in native ownership order: source enable/state, waveform or sample selection, then the channel/lane level trim. Avoid placing the level row at the card's lower edge when there is unused vertical space above it; the level control is part of the voice, not a footer.

High-density, sampler, and wavetable families may use inline master-detail organization inside the unified surface. Every compact card keeps source identity, enable state, and level or native amplitude state visible; the precision editor remains spatially connected to that deck and never becomes a top-level destination. Its controls bind to the same APVTS parameters as the cards, so host automation and MIDI remain authoritative.

Wavetable chips that lack native ADSR should not show empty or generic "envelope" placeholders. HuC6280, Namco WSG, and SCC expose a shared `Chipper Gate` in their two-row footer. These are musical helpers layered over native volume state, not authentic ADSR. Per-channel wave and level controls stay inside the source cards.

## Slot Scalability

The old six-card grid is a convenience template, not a product rule. Every chip should preserve the same conceptual zones:

- Chip profile and context.
- Sources, voices, lanes, samples, or operators.
- Tone, shape, filter, operator, or sample editor.
- Envelope, gain, level, or native attenuation behavior.
- Motion, performance gestures, and musical helpers.
- Output, utility, telemetry, and status.

Chip manifests may choose different panel templates and layout density inside those zones. The equal six-card grid is only a fallback layout. Chips with a larger native control surface may use a chip-specific layout template while preserving the same conceptual zones and stable parameter IDs. SID is the first proof point: three deep voice cards own waveform and pulse width, sync/ring sits immediately below the follower voices it affects, the 6581/8580 choice is part of the complete filter/model block, and the per-voice Envelope surface spans the full width because ADSR is central to using the chip. PSG, wavetable, and most sample chips fit a standard channel-bank layout. FM chips should use the same conceptual zones but need a denser operator editor or operator grid inside Tone / Shape. Sample-heavy chips such as SPC700-style and Paula modes should use sample voice banks plus sample/loop/pitch panels instead of oscillator-style controls.

SPC700-style mode uses five simultaneous regions rather than a generic module grid. `Generated Source` owns the fallback generated sample shape and the shared NON/noise-source choice; `Voice Shaping` owns the shared envelope recipe, Pitch/PMON gesture, and ADSR/GAIN speed. `Sample Voices` keeps all eight playable lanes visible in a four-by-two matrix, with enable/state, waveform evidence, loaded-bank slot pin, and level in every card. `Sample Bank` owns file/folder/bank import, manual or mapped playback, map root, loop lifetime, waveform preview, and loop-point overrides. Only Voice Spread, Echo Color, Voice Volume, modern Stereo Spread, and Output remain in the shared footer. This organization is intentionally honest about the current partial core: the shaping controls are shared templates until independent per-voice S-DSP state exists in the engine.

Paula uses a different sampler structure. `DMA Sample Channels` keeps the four fixed L/R/R/L hardware lanes visible in a two-by-two matrix; each card owns enable/state, waveform evidence, generated shape, loaded-bank slot, modern post-volume trim, resolved 0-64 volume, and loop/one-shot state. `Sample Bank` owns WAV/AIFF/8SVX/MOD import, manual/key/tracker mapping, root, missing-asset status, and loop-marker waveform evidence. `Tracker Playback + Paula Output` is a two-row shared strip for Channel Spread, Period Motion, Loop Tendency, explicit Loop Mode, Channel Volume, the Chipper Tracker Amp Env helper, Paula Output Filter, modern width, and final Output. Full width means authentic L/R/R/L hard pan; zero width is disclosed as a modern centered collapse. Paula has no native ADSR, and the current partial core applies loop mode, volume, period motion, and the amp helper as shared behavior rather than inventing independent per-channel parameters.

Sampler and wavetable layouts are allowed to spend vertical space differently from the compact PSG/FM fallback. Keep those height budgets explicit per chip family so SPC700 and Paula sample-bank editors cannot be compressed by an unrelated fallback branch, and so HuC6280/Namco/SCC source cards keep enough room for per-lane wave selection plus level.

The product rule is: every chip feels distinct, but no chip feels like a different plugin.

## Adaptive System Views

The adaptive UI should change structural complexity to match the selected chip's native limitations:

- **Raw 8-bit generators:** NES/RP2A03 and SN76489 should emphasize hard-edged channel strips, discrete register choices, and simple source routing. Pulse duty is a segmented register selector, not a pulse-width slider. Triangle-style channels should avoid fake volume-envelope controls when the hardware lacks them. Noise and PCM-like sources should prefer discrete period selectors, grit controls, or sample-trigger surfaces over generic pitch knobs.
- **Multi-voice analog hybrid:** SID should feel like a compact laboratory synth: three deep voice lanes, per-voice waveform/register controls, per-voice ADSR, oscillator interaction, and a global filter matrix with cutoff, resonance, mode bits, and explicit voice routing. SID waveform controls must allow the chip's combined waveform bits where the engine supports them rather than pretending each voice is a one-wave oscillator forever.
- **Two-operator FM:** OPL2/YM3812 and related FM chips should move away from oscillator strips and toward operator blocks, algorithm/feedback structure, multiplier, key-scale/rate controls, envelope stages, and graphical waveform selectors for the native mathematical shapes.

Chip-specific layout templates should reserve real space for the controls that define the chip. NES Noise Mode and Noise Period live together in the Noise card; DMC has its own fifth lane plus a full native sample/DAC/rate section. Sample-based chips such as SPC700-style and Paula get a taller unified surface so sample playback mode, slot selection, loop controls, status text, and waveform previews can coexist without overlapping.

These views should reuse the same shell, typography, APVTS parameters, MIDI mapping strategy, and descriptor-driven metadata. The variation belongs in layout templates and chip-native components, not in unrelated visual skins.

## Component Strategy

Use JUCE's native plugin-safe controls for DAW-facing behavior: `ComboBox` for selectors, `Slider` for continuous automatable parameters, `Label` for readouts/status, and button-style controls for future discrete actions. Add Chipper-specific presentation components only where the chip metaphor needs structure that generic controls do not provide.

The first custom surface is the NES channel card grid inside Sources. It keeps the stable shell and exposes Pulse 1, Pulse 2, Triangle, Noise, and DMC as five distinct channels. Source 4 gates and trims Noise; Source 5 independently gates DMC. DMC deliberately has no conventional source-level trim: its card reports the native `$4011` 7-bit DAC state, while the DMC Channel section owns file/bank loading, rate, loop, mapping, and waveform state. Similar chip surfaces should follow this pattern: PSG channel banks, FM operator grids, sampler voice banks, wavetable editors, and macro/readout tiles. These components should reflect stable parameters and tested engine behavior rather than presenting fake controls for planned features. Shared sample-bank dropdowns are map-aware: Manual Slot lists numbered files, while Note Map, Drum Map, Sample Map Only, and tracker map modes prefix each active slot with the MIDI note that will trigger it from the current map root.

NES and DMG Pulse Duty use segmented register-choice components because RP2A03 and DMG pulse duty are four-state register fields, not continuous PWM values. NES exposes Pulse 1 through `macroControl1` and Pulse 2 through `pulse2Duty`; DMG mirrors that pattern as Pulse 1 Duty over `NR11` and Pulse 2 Duty over `NR21`, because Game Boy pulse channels can choose their duty cycles independently. `Follow` preserves the current preset-friendly pairing behavior for Pulse 2, while explicit choices write the channel-2 duty bits independently and show the resolved register bits in the live readout. NES and DMG place these register choices in the owning channel cards: pulse cards own duty, wave cards own wave/sample-shape plus level choices, and noise cards own noise mode/period behavior. Embedded channel-card readouts must stay short and resolved: Pulse 2 shows `Follow -> 50%` or `75% independent` in the card, while the detailed register string such as `NR21 bits 11, 75%` remains available in the status text or tooltip. DMG Sweep Shift uses `macroControl2` as a chip-aware slider over the `NR10` channel-1 sweep shift bits. NES Noise Period and DMG Noise Clock use `macroControl3` as chip-aware sliders over `$400E` and `NR43` noise fields, while YM2149 Noise Pitch uses the same stable parameter over the 5-bit shared noise period in register 6.

SID exposes three independent oscillator voices through the source cards. Voice 1 Pulse Width uses `macroControl1`; Voice 2 and Voice 3 have dedicated 12-bit pulse-width sliders/readouts mapped to their own SID register pairs. All three pulse-width controls are presented only inside their owning voice cards rather than duplicating Voice 1 in the shared footer. SID Cutoff uses `macroControl3`, Resonance uses `stereoSpread` as a SID-specific `$D417` register role, and the SID Filter Mode control uses a dropdown because the nine `$D418` mode-bit choices are too dense for readable segmented buttons. SID Filter Routing also uses a compact menu because its nine `$D417` low-bit choices are too wide for a segmented row.

SID Sustain uses `macroControl4` as the musical SR sustain source, SID ADSR Speed uses `envelopeDecay` for macro attack/decay/release templates, and each SID voice has its own Attack, Decay, Sustain, and Release stepped vertical override controls for `Follow` plus exact 0-15 AD/SR nibbles. Each Sustain control's `Follow` choice uses the `macroControl4` Sustain slider, while explicit values write that voice's SR high nibble directly. The compact value labels show `F->n` when a lane follows the macro-resolved nibble and `n` when a lane is explicitly pinned, so users can read the effective register state without opening dropdowns or hovering tooltips. Readouts also show the resolved V1/V2/V3 AD/SR register bytes and A/D/S/R nibbles so both the shared musical control and exact per-voice overrides feel chip-aware.

Full ADSR controls belong only on chips with native ADSR behavior, such as SID and S-DSP/SPC700. FM chips should use `Operator EG` language because YM2612, YM2151, OPL, and OPLL use chip-specific operator envelope generators rather than generic synth ADSR. PSG/APU modes should expose their native envelope, length, attenuation, or decay controls, while wavetable and sample chips without native envelope generators should label musical shaping as a Chipper amp-envelope helper. SID Voice 1 Wave uses the stable `waveShape` parameter, while SID Voice 2 Wave and Voice 3 Wave use dedicated stable menu parameters so the UI can expose independent oscillator waveform choices without asking users to edit control-register bytes. `Preset` uses the selected SID recipe or Voice 1 choice; explicit Triangle, Saw, Pulse, and Noise choices map to each voice's SID control-register waveform bits.

SN76489 Noise Bias also uses `macroControl3`, but only when Noise Mode is `Preset`: it biases the macro-selected PSG noise-control register and explicit Noise Mode choices override it. POKEY Distortion Bias uses the same slot for AUDC-style distortion character when Distortion Code is `Preset`. YM2149 Tone/Noise Mix uses the same pattern over `macroControl4`: `Noise`, `Tone`, and `Both` map to register 7 mixer bytes rather than a fake blend. NES Noise Mode, NES Pulse 2 Duty, DMG Noise Mode, DMG Wave Shape, SID ADSR nibble menus, SID per-voice waveform menus, SID Filter Mode, SID Filter Routing, YM2149 Envelope Shape, SN76489 Noise Mode, and POKEY Distortion Code follow the same pattern through `ChipParameterSpec` metadata. Future chip controls should follow the same rule: use continuous controls only for continuous behavior, segmented/stepped controls for register-like behavior, dropdowns for wide register choices, and macro controls only when they intentionally map a musical gesture to chip-native states.

YM2149 Envelope Shape is a compact register menu over the shared CC90 parameter. It keeps the musical shortcuts `Fixed`, `Fall`, `Rise`, `Saw`, and `Triangle`, then exposes exact AY/YM register-13 shape codes `0x00` through `0x0F` for users who want hardware-level control. The Shared Hardware Envelope module draws a state preview from the same shape-code helper used by the audio core: fixed-volume mode is shown as a flat level, while enabled hardware-envelope modes draw the resolved register-13 contour. YM2149 Channel Mix is the first compact per-channel register menu surface. Channel A, B, and C each expose `Follow`, `Tone`, `Noise`, `Both`, and `Off`; `Follow` uses the default Tone/Noise Mix, while explicit choices override that channel's register 7 tone/noise enable bits. The UI readout reports the resolved mixer byte and A/B/C choices, and MIDI CC101-103 plus renderer flags use the same APVTS parameters. The UI deliberately presents only A/B/C as output channels: register 6 produces one shared noise signal, whose enable, trim, pitch, and default routing live together in Shared Noise + Routing instead of masquerading as a fourth note-allocated voice.

Segmented controls must lay out only the legal choices for the active chip. The shared Noise Mode parameter has three visible segmented choices for NES/DMG, while SN76489 uses a dropdown so full labels like Periodic Low, White Low, and White Tone 3 can describe the PSG noise-control register without abbreviation. SPC700 sample lifetime uses a checkbox-style `Loop` toggle because looping is a binary performance choice once the playback mode is chosen; this remains intentionally separate from the Sample Playback dropdown that chooses Manual Slot, Note Map, or Drum Map. The shared YM Envelope Shape / SID Filter Mode parameter uses dropdowns for YM's full hardware envelope shape set and SID's nine `$D418` filter-bit choices. The editor reflows each row from the active `ChipParameterSpec` instead of reserving blank maximum-capacity slots. Dropdowns, numeric readouts, and sample selectors should use the same readable control height wherever possible; shrinking sample selectors or pitch readouts to fit a cramped row is a layout bug, not an acceptable density tradeoff. Sampler-style cards should prioritize visible controls and waveform previews over dense explanatory readouts; register/status text belongs in tooltips, footers, or roomy summary areas when the card would otherwise overlap.

POKEY uses a 2x2 channel matrix because that is the smallest layout that communicates both hardware relationships at once: channels 1+2 and 3+4 form the two possible 16-bit pairs horizontally, while channels 3 and 4 clock the modeled high-pass paths into channels 1 and 2 vertically. When pairing is active, the high-byte channel is visibly consumed, its inactive source/trim controls are disabled without changing parameter state, and Chip Poly labels renumber the remaining three or two note lanes. Channels 3/4 remain identified as high-pass clocks because the partial core advances a filter clock even when that channel's audible output is muted.

The current partial POKEY core resolves one shared AUDC distortion code and AUDV base for sounding lanes, so Distortion Code, preset-only Distortion Bias, and the modern AUDV Gate belong in one Shared AUDC Texture + Gate block rather than being duplicated into four misleading channel controls. Channel sliders are labelled as post-AUDV trims because they are modern gain controls after the shared AUDV nibble, not independent native volume registers. AUDCTL Pairing and AUDCTL Filter sit together in a separate relationship block with resolved register readouts.

NES, DMG, SID, YM2149, SN76489, and POKEY source controls are stable non-macro controls. They draw from the universal `source1Enabled` through `source9Enabled` parameter pool as needed. NES uses five distinct lanes: Pulse 1, Pulse 2, Triangle, Noise, and DMC. DMG, SN76489, and POKEY expose four output lanes; SID intentionally exposes three because external input is not implemented. YM2149 uses four source parameters but only three output-channel cards: A/B/C are note-allocated channels, while source 4 is the shared noise-generator gate/trim embedded in its routing module. Conventional output-channel cards own a compact modern level trim where that is honest. NES DMC is the deliberate exception: Source 5 controls its enable, while the native `$4011` DAC value replaces a fake source-level slider. Source scopes visualize resolved chip state rather than realtime audio; the output scope alone uses allocation-free processor telemetry. Chip layouts may reflow these shared components, but every active card must represent an audible output channel or an explicitly labeled shared generator, and every native control must stay with the channel or shared hardware block it actually affects.

FM-family source cards should show useful native state even before the full operator editor lands. YM2612/OPN2 and YM2151/OPM cards expose resolved algorithm, feedback, representative operator multiples, and carrier/modulator total levels; OPN-family embedded SSG cards expose the resolved tone/noise/off mixer state and envelope flag; OPL2 cards expose resolved waveform, connection, feedback, modulator multiple, and modulator/carrier total levels; YM2413/OPLL and NES + VRC7 cards expose the resolved ROM instrument/volume state or `User0` when the shared editable OPLL user-patch slot 0 is active. In YM2413 rhythm mode, source cards 7-9 should read as BD, HH+SD, and TOM+CYM and disclose the `$0E` key bits plus `$36-$38` volume nibbles rather than pretending they are plain melodic lanes. These readouts are not a substitute for deeper operator-grid UI, but they make the current audible presets inspectable and keep the visible surface tied to the register writes sent into ymfm or emu2413.

YM2612 and YM2151 use an algorithm-first UI component. Their Algorithm controls use dropdowns rather than crowded segmented rows because the legal set is Preset plus eight four-operator algorithm values. The adjacent preview draws the operators, modulation edges, and carrier outputs from the same `ym2612AlgorithmForPatch` or `ym2151AlgorithmForPatch` helper used by the engine path, while tooltips report the resolved `$B0` OPN2 or `$20` OPM algorithm and feedback bits. The operator surface labels each four-op slot as carrier (`C`) or modulator (`M`) from the same resolved algorithm, places the APVTS-backed OP1-OP4 Level trims in those rows, and keeps multiplier, total-level, and envelope register bytes visible. Both chips now give this shared patch a dedicated unified layout: Algorithm, Feedback, Operator Tone, and FM Level sit together beside the shared four-operator matrix, while only clock and final output remain in the compact footer. OPN2 keeps Envelope Shape, channel-6 DAC Mode, native LFO Depth, and pan in its routing row. OPM instead keeps native `$0F` noise inside channel 8 and groups `$18/$19/$1B` LFO depth with `$20+n` pan routing. Algorithm Bias is enabled only when the Manual recipe and Preset algorithm mode actually allow it to own the register.

The other FM chips should not inherit the OPN2/OPM layout blindly. OPL2/OPL3 treats topology as the primary musical decision: one stable 3x3 lane matrix resolves to nine independent 2-op voices, six melodic voices plus the `$BD` percussion set, nine low/high-bank layers covering channels 1-18, or native `$104` pairs 1+4, 2+5, and 3+6 with channels 7-9 left independent. In 4-op mode cards 1-3 remain key lanes and cards 4-6 become visibly disabled operator-stage followers while retaining meaningful level trims. YM2151/OPM exposes all eight lanes in a 4x2 bank and makes channel 8's `$0F` noise ownership explicit; the current patch and operator controls are shared across lanes because the engine parameters are shared. Its genuine next gaps are independent per-channel patches, direct LFO waveform/sensitivity editing, DT1/DT2 detune, timer/CSM behavior, and stronger noise/hardware validation. YM2413/OPLL starts from a ROM-instrument dropdown because the useful first choice is the preset patch family, not a free oscillator waveform. Its dedicated 3x3 lane matrix keeps all nine melodic/rhythm roles visible; Instrument and `$0E` topology share one block; and the shared User0 Mod/Carrier cards make it explicit that all channels using Custom consume the same programmable `$00-$07` patch slot. Explicit ROM instruments disable that editor without erasing its settings. The larger OPLL/VRC7 engine pass should add patch-set variants, mixer calibration, split rhythm tuning, and stronger validation.

YM2203/OPN is a coupled FM-plus-SSG instrument rather than a smaller OPN2 panel. Its dedicated 3x2 lane bank pairs FM1/SSG A, FM2/SSG B, and FM3/SSG C for Big Mono while exposing six independent allocation positions in Chip Poly. Algorithm, feedback, FM envelope shape, and four operator rows are one shared FM patch. Each SSG lane owns its register-7 Tone/Noise override, while one shared SSG generator owns envelope shape and the `$0B/$0C` period. The footer keeps only `FM Tone + SSG Noise` and `FM + SSG Level`, because those two implemented parameters intentionally bridge operator tone/carrier level with SSG noise period/amplitude. Algorithm Bias is contextual, and native Feedback is explicitly pitch-neutral so FM and SSG pairs cannot drift apart.

YM2608/OPNA extends that coupled model without pretending its rhythm and sample paths are extra melodic lanes. A 3x3 bank keeps six FM and three SSG allocation lanes visible. Drum/Hit relabels FM1-6 with BD, SD, Top Cym, HH, Tom, and Rim because their existing enable/level parameters also gate and scale the six ADPCM-A rhythm instruments; the generated/user rhythm ROM and optional encoded ADPCM-B memory remain conditional layers in one separate signal-path block. SSG A-C retain local mixer ownership and share one envelope shape/period generator. The footer carries only controls that genuinely cross engines or terminate the path: FM/SSG tone and level, native pan, modern stereo spread, clock, and output. Feedback writes `$B0` only and is tested not to change FM pitch.

The OPL surface keeps `OPL Topology`, Waveform, Connection/Operator Balance, Feedback, Operator Tone, and FM Level together in one shared patch. The Waveform control uses a dropdown plus a preview of the resolved YM3812 waveform register because the shapes are mathematical operator modes and need readable names. The adjacent Pair/Mod/Car cards report the resolved routing, multiplier, total-level, envelope, waveform, and `$104` state without pretending the current shared patch is a deep per-operator editor. `Active Signal Path` explains the selected topology, and only Clock and Output remain global. The stable `opl.rhythmMode` automation ID remains unchanged; only its visible descriptor label changed to `OPL Topology` because most choices are not rhythm modes. Direct per-operator ADSR, vibrato/tremolo/KSR/KSL flags, stereo-bus routing, and a full four-operator algorithm editor remain genuine product gaps.

FM Performance readouts should expose resolved register state, not just normalized macro values. YM2612/OPN2 and YM2151/OPM feedback now reports the 0-7 feedback field, resolved algorithm, and channel algorithm/feedback register byte (`$B0` for OPN2, `$20` for OPM); their core debug JSON also exports per-operator carrier flags so preset QA can confirm the same carrier/modulator topology shown in the Operator EG readout. YM2612/OPN2 LFO Depth reports the resolved `$22` enable/rate and `$B4+n` AMS/PMS bits, while YM2151/OPM noise reports the resolved `$0F` enable/frequency byte and OPM LFO Depth reports the resolved `$18` rate, `$19/$1A` AM/PM depths, `$1B` waveform, and `$38+n` sensitivity byte. OPN/OPNA/OPNB SSG readouts report register `$07` mixer bits, shared noise period, envelope shape, and envelope period for the embedded SSG lanes. OPL2/OPL3 feedback reports the 0-7 feedback field, `$C0` connection register byte, serial/parallel connection state, and `$104` value in 4-op Pair mode. The renderer debug JSON pins these same register bytes so the visible UI language stays tied to the chip adapter rather than becoming decorative text.

Four-operator FM surfaces use the shared `ChipperFmEditor` rather than a compressed generic row. Its 2x2 grid marks carrier cards with the chip primary color and modulator cards with the accent, keeps level, multiplier, and combined envelope-rate overrides reachable on every operator, and leaves the complete resolved register string visible within the owning card. Chip-specific layouts decide where the shared algorithm graph and patch-level controls belong. YM2612 places them beside the operator matrix on the same unified surface at both supported widths instead of hiding them behind a workspace destination.

Wavetable and sampler chips need distinct structural templates. HuC6280 now presents six 32-sample/5-bit voice cards, labels channels 5/6 as wave/noise lanes, and places `Ch 2 -> Ch 1 Pitch LFO` directly beneath the cards. Preset resolves per recipe, Off keeps channels independent, and Light/Deep/Fast make channel 2 a muted wavetable modulation source for channel 1 while the readout reports rate, depth, and voice cost. The stable macro-control slot now drives both the implemented 5-bit upper-channel noise period and LFO depth; the remaining first-class editor gap is direct Wave RAM drawing/import plus native balance registers. Paula uses four hard-panned sample strips with fixed left/right clustering, period/volume registers, optional modern width, hardware LED/static-filter controls, and AM/FM channel-pair modulation. POKEY uses a four-channel deck centered on AUDC distortion/poly counters, 16-bit channel-pair switches, clock-rate choices, and high-pass pair routing rather than generic oscillator controls.

Wavetable-family source cards follow the same ownership rule. HuC6280 headers prioritize Wave RAM, LFO target/source, and upper-channel noise roles. Namco WSG headers show lane number, 4-bit Wave RAM, and resolved 0-15 volume; Chip Poly adds Note 1-8. SCC headers show channel number, 32-byte Wave RAM, and resolved 0-15 volume; Chip Poly adds Note 1-5. Namco and SCC selectors own the generated lane/channel template, and renderer RAM checkpoints prevent those controls from becoming metadata-only again. Their shared `Pulse Width` control is enabled only when at least one visible source resolves to Pulse. SCC's `Gesture Pitch` is similarly available only to the Sweep Zap and Jump recipes that actually consume it. Source cards reserve Level immediately after the selector so gain remains reachable.

Performance Macros are a secondary live-control surface. Compact macro cells should show the label and bound control first; detailed resolved register readouts stay in tooltips, the footer/status text, or the preset summary unless the cell has enough height for a full readout line below the slider. This keeps DAW-fit chip pages readable without hiding the controls themselves.

HuC6280, Namco WSG, and SCC keep `Chipper Gate` in their shared two-row footer. None is labeled as native ADSR: the native chip surface remains per-lane Wave RAM, enable/key, frequency, and volume state.

Implemented chips with many native lanes must still expose the entire modeled signal path. YM2151 now fits eight FM channels in a 4x2 bank and YM2413 fits nine melodic/rhythm lanes in a 3x3 bank; SPC700-style, HuC6280, Namco WSG, YM2612, OPL2/OPL3, and SCC likewise expose all modeled lanes with visible source cards, host parameters, MIDI CC mappings, enable toggles, and level controls. The descriptor layer owns these visible/native counts and tests pin the contract.

Noise Mode is now chip-aware. NES/RP2A03 choices map to `$400E` bit 7 for long LFSR noise versus short-loop metallic noise, DMG choices map to `NR43` bit 3 for 15-bit versus 7-bit polynomial noise, and SN76489 choices map to the PSG noise-control bits. SID Osc Interaction reuses the same stable APVTS/CC91 slot in SID mode, but its descriptor relabels it as a segmented register control for Off, Sync, Ring, and Both choices that write the voice control-register sync/ring bits; it lives directly under the three voice cards rather than in a detached Motion destination. DMG Wave Level maps to `NR32` channel-3 output-level bits with Preset, Mute, 100%, 50%, and 25% choices, giving the Wave RAM channel a real hardware level selector instead of a generic gain slider. CC94 is a shared chip-choice slot whose host-facing name is intentionally generic (`Chip Choice / Route`) because each chip descriptor gives it the user-facing meaning for that mode. DMG uses it as `NR51` Stereo Route, SID uses it as SID Model, SPC700/Paula use it for sample lifetime/loop behavior, HuC6280 uses it for Ch 1/2 LFO behavior, POKEY uses it for AUDCTL pairing, FM chips use it for pan/routing choices, and some wavetable lanes use it for the final per-lane wave selector. SN76489 Noise Level maps to the PSG attenuation nibble for the noise channel. YM2149 Noise Pitch maps to register 6, YM2149 Tone/Noise Mix maps to register 7 mixer bits for noise-only, tone-only, or combined tone+noise output, and YM2149 Envelope Speed maps to the 16-bit envelope period register pair feeding the stepped envelope counter. Stereo Spread is an Output-module convenience for mono-native PSG chips: YM2149/AY spreads A/B/C left/center/right, SN76489 spreads Tone 1/2/3 left/center/right and keeps noise centered, and the default zero value preserves mono chip output. YM2612/OPN2 and YM2151/OPM reuse the same stable CC93/APVTS slot as `LFO Depth` in the Motion module because their high-value motion path is native FM LFO depth rather than post-chip stereo width. In each case `Preset`, `Follow`, or `Auto` preserves the chip-specific recipe, follows another live control, or derives a mode-aware value, and the readout should show the resolved register value. This establishes a broader rule: preset selections are per-chip musical recipes, and visible readouts should reflect the resolved chip state rather than only raw control offsets.

All current APVTS parameters also have fixed MIDI CC mappings. The Chipper-owned fixed map currently spans CC24-119 so every exposed host parameter remains controllable without using MIDI channel-mode controllers 120-127. NES mode surfaces DMC Direct, DMC Rate, Loop, Playback Mode, Map Root, and a compact DMC sample bank control in the Performance strip because those are more musical than a generic clock override during normal patch design; the global clock parameter remains available to host automation and MIDI. The VST can load a single `.dmc` file as a one-slot bank or stage a folder of `.dmc` files into a local checklist; checked entries form up to 32 active in-memory slots, then the active sample dropdown and CC117 select the same bank slot. The bank editor includes First 32, Invert, and Clear actions so a user can quickly curate large folders without loading, copying, or committing sample content. In Note Map, MIDI notes from the DMC Map Root upward select checked slots on the monophonic DMC lane without changing the manual slot parameter; notes outside the active mapped span clear the DMC lane instead of clamping to the first or last checked slot. The DMC sample status line stays compact but reports selected or mapped bytes, estimated playback duration, rate index, one-shot/loop state, mapped key span, and runtime state (`playing`, `stopped`, or `ready`) where available; its tooltip adds bit count, bit-clock, loop-bit detail, and bits-stepped detail so users can diagnose rate mismatch without leaving the instrument. WAV-to-DMC conversion remains planned, not active in this build. Factory presets are presented as chip-local banks: the Preset menu filters to the selected chip, shows the available count, and the Performance summary repeats that count until a preset is selected. The command-line renderer can step one external `.dmc` path at a selected DMC rate index, `$4010` loop-bit setting, and optional DMC-only channel mask today. CC74 and recipe-only host automation are event-like: changing the Preset Recipe parameter applies the selected chip's internal recipe to native controls, source enables, source levels, envelope helpers, and chip-specific choice parameters, then users may continue tweaking individual controls. When a preset or state restore changes the recipe and control values together, the processor preserves that snapshot rather than reapplying the recipe. The shared control registry is JUCE-free so the renderer, descriptor tests, and plugin all read the same default CC map. The editor appends the relevant CC number to automatable control tooltips and shows a footer CC-range badge whose tooltip lists the full map, so hardware control is discoverable without cluttering the main surface. Renderer descriptor JSON exports both per-control CC metadata and a top-level `midiCcMappings` list, giving future dynamic UIs and scripts a single machine-readable parameter map. When adding a new automatable APVTS parameter or surfacing a new chip descriptor control, add its role-to-parameter mapping, default CC, UI tooltip/readout, descriptor metadata, and regression coverage at the same time so the plugin remains fully controllable from MIDI hardware.

## Data Model

User presets remain portable flat files rather than a plugin-private database. The editor scans `Documents\Chipper Presets` for `.chipperpreset` files, filters them by saved chip metadata, and adds them to the same Preset browser under a User Presets section. Files saved by Chipper include role, engine, tag, note, and source attributes so user presets can participate in the same metadata filter and search path as factory presets while older flat files still load normally. Loading one restores the APVTS state, register snapshot, and portable sample references from the file; Save writes back to the loaded file, Save As writes a new shareable copy, and saving a new sound asks for a `.chipperpreset` path. A loaded external preset is also listed for the current editor session when it matches the active chip, keeping shared/downloaded sounds visible before the user decides whether to Save As into their bank. The browser's top-level Init Patch entry is not a factory sound or a file; it creates a neutral chip-local patch with centered controls, native sources enabled, and no curated motion while preserving the current Strictness and supported Play Mode.

The UI should be built from chip definitions instead of per-chip hardcoded editor branches.

```cpp
enum class ControlType
{
    knob,
    slider,
    toggle,
    segmented,
    menu,
    waveButtons,
    meter
};

enum class ParameterKind
{
    continuous,
    discreteChoice,
    steppedNumeric,
    booleanToggle,
    macro,
    chipRegister,
    hiddenInternal
};

struct ChipParameterSpec
{
    std::string id;
    std::string label;
    std::string unit;
    ControlType controlType;
    ParameterKind kind;
    float minValue;
    float maxValue;
    float defaultValue;
};

struct ModuleSpec
{
    std::string id;
    std::string title;
    std::vector<ParameterSpec> parameters;
};

struct ChipSpec
{
    ChipMode mode;
    std::string displayName;
    std::string modelLabel;
    std::vector<ModuleSpec> modules;
};
```

The editor asks the selected chip spec what modules and controls to show. The UI should not need SID, NES, or YM2612-specific register knowledge; that belongs in the chip adapter and engine mapping layer. The current implementation has started this migration with `ChipParameterSpec`, `ParameterKind`, and `ControlSurface` declarations in `ChipDescriptor`; live macro-control labels, source-card help, and segmented/register surfaces are descriptor-driven where practical. User-visible chip modes should represent named hardware families with playable or truthfully partial cores, not generic placeholder modes.

## Parameter Strategy

DAW automation IDs must remain stable after plugin load. Chipper should use a hybrid parameter strategy:

- Universal automatable macros for common musical performance controls.
- Universal source-enable and source-level parameters for finite native channels or source lanes.
- A universal Play Mode parameter for how one patch uses native chip channels.
- Stable chip-specific parameters grouped by chip and module.
- Inactive chip parameters hidden from the Chipper UI, but not created or destroyed dynamically.
- Internal chip state and register snapshots saved in presets when needed.

The internal Macro parameter remains a stable automation slot, but the UI presents it as a preset recipe. Its displayed choices and defaults are chip-specific. For example, "Drum" on NES should resolve to pulse/triangle/noise APU behavior, while "Drum" on SN76489 should resolve to PSG attenuation and noise-register behavior. When a preset recipe changes, the UI should update labels, segmented state, and readouts to show the effective chip settings produced by that recipe. The current bridge keeps one stable enum for DAW automation and writes the selected chip recipe into stable native control parameters so the visible controls match the audible patch. A recipe should not appear in the factory browser unless it maps to an implemented, audible chip surface and passes the preset catalog checks.

The compact Performance strip is the current patch-state surface, not a separate hidden control bank. It should prefer short labels, chip-aware readouts, and tooltips over explanatory prose. Each macro readout should name its destination before the resolved state, for example `$400E noise`, `NR43 noise`, `$D415 cutoff`, `AUDV gate`, `Wave RAM`, or `$B0 feedback`, so users can tell whether a control is changing a native register, a chip-specific helper, or a modern performance layer. When a factory preset is selected, the strip names that preset before the resolved macro/register summary so users can see that the visible controls represent a preset snapshot rather than an abstract macro label alone. Source-card layouts should also be bounded rather than merely compact: a card needs enough height for its waveform preview, native selector, and level lane, while avoiding the tall blank panels that made wavetable chips feel less intentional. The editor smoke gate owns that minimum and maximum readable range for wavetable source cards, and it now exercises every chip at the 1180 px compact-width contract so a narrow host window cannot reintroduce clipped controls that only fail outside the default 1240 px view.

SID keeps waveform and pulse-width controls in the three voice cards because both are per-voice register decisions. The interaction row immediately below them makes the shared follower-voice sync/ring choice visible without inventing separate modulators. Filter + SID Model keeps cutoff, resonance, filter mode, voice routing, and the partial 6581/8580 response profile together instead of scattering causal controls into Profile, Motion, or Performance destinations. SID ADSR is per voice, so overrides need a roomy primary surface with explicit Attack, Decay, Sustain, and Release controls for each voice plus envelope previews. That surface is a full-width SID panel rather than a squeezed half-width card, and layout tests keep its content inside the panel and clear of Performance + Output at both default and compact widths. Output monitoring reserves enough height for the final audio scope to be legible as a waveform, not a decorative trace.

Preset recipes are lightweight chip-specific snapshots: they can set native controls, source enables, envelope helper defaults, resonance/spread helpers, and chip-specific choice parameters such as NES Pulse 2 Duty, NES Noise Mode, DMG Noise Mode, DMG Wave Shape, DMG Stereo Route, SID Filter Mode, SID Filter Routing, SID Osc Interaction, SID Model, YM Envelope Shape, and SN76489 Noise Mode. Applying a recipe resets the universal source level trims to unity, resets inherited recipe-driven register choices to `Preset`, `Follow`, or chip-specific `Auto`, resets SID Voice 2/3 Pulse Width to the selected recipe's pulse-width value, and keeps explicit overrides available afterward, so users hear the curated voice/envelope/mixer stack first and can then override individual NES pulse duty, SID oscillator waveforms, filter routes, per-voice pulse width, per-voice ADSR nibbles, or YM channel mixer states manually or from MIDI. Factory presets are curated snapshots over those same stable parameters, not separate sound engines, and may pin source-level balances, DMG Wave Level, SID Voice 2/3 Waveform, SID Voice 2/3 Pulse Width, `$D418` Filter Mode, `$D417` Filter Routing, and per-voice SID ADSR nibble menus when a preset needs a specific mixed oscillator/filter/envelope stack. Each live-chip preset stores chip mode, Strictness setting, preset recipe, play mode, native controls, source enables, source-level trims, chip-specific choices, DMG Wave Level, SID voice-wave/pulse-width/filter-routing/ADSR overrides where needed, and output trim. The VST applies those snapshots to APVTS parameters so DAW state remains ordinary plugin state, while `chipper_render --preset` uses the same catalog and output trim for regression coverage. Renderer debug JSON includes the active descriptor's recipe, parameter, choice, output trim, and preset metadata so automated tests can verify that the UI/control vocabulary matches the engine-backed chip surface. Non-audible roadmap ideas belong in docs, not the executable preset browser.

`chipper_render --list-descriptors --debug descriptors.json` exports the same chip descriptors, preset recipes, parameter specs, visible/native source-lane counts, default MIDI CC map, and factory preset catalog without rendering audio. `chipper_render --describe-chip nes --debug nes.json` exports the same schema for one chip. This is the machine-readable contract for future dynamic UI work: chip-aware controls should be proven in descriptor metadata before the editor grows more chip-specific surfaces.

## Patch And Channel Model

Chipper exposes one patch per plugin instance. A patch can use every native chip channel inside the selected chip core, but users should not have to compose like a tracker by default.

- **Big Mono:** all useful native channels contribute to one played sound. This is the default.
- **Chip Poly:** overlapping notes allocate across finite native chip channels where the core supports it.
- **Manual:** reserved for explicit channel assignment and tracker-style routing.
- **Clone:** reserved for Hybrid mode engine cloning, where each MIDI note can own a virtual chip stack.

Only Big Mono and Chip Poly should be visible in the VST UI until Manual and Clone have engine implementations. Chip Poly should be enabled only for chip descriptors with tested finite-channel allocation; unsupported chips resolve requests back to Big Mono. Internal enums and renderer parsing may reserve those future modes, but visible controls should not imply behavior that does not exist.

UI controls should graduate from descriptor text to real controls only when they have an engine mapping, stable parameter identity, preset recall behavior, and renderer coverage. Roadmap controls can be described in docs, but should not appear as fake knobs before the core exists.

## Module Mapping

Equivalent concepts stay in equivalent places:

- NES / RP2A03: Sources are Pulse 1, Pulse 2, Triangle, Noise, and DMC. Pulse duty lives with each pulse, Noise owns mode/period, and DMC owns sample/DAC/rate behavior.
- Game Boy / DMG: Sources are Pulse 1, Pulse 2, Wave, Noise; each source card owns its native register controls, so Pulse 1/2 duty, Wave RAM shape/level, and Noise width live with their channels instead of in a separate Wave / Noise panel.
- SID / C64: Sources are Voice 1-3; Tone becomes Filter.
- YM2149 / AY: A/B/C are the three output channels and Chip Poly lanes. Their cards own `Tone`, `Noise`, `Both`, or `Off` register-7 overrides. The single register-6 noise generator is shown separately inside Shared Noise + Routing with its enable, trim, pitch, and default routing; the single register-13 envelope generator sits beside it in Shared Hardware Envelope.
- SN76489: Sources are Tone 1-3 and Noise; the Noise source card owns the PSG noise-register mode, so no separate Tone / Noise panel should appear unless it contains backed controls.
- Philips SAA1099: Sources are six stereo Channels 1-6, arranged visibly as generator groups 1-3 and 4-6. Every channel card owns enable, modern trim, and its resolved left/right 4-bit amplitude state. Noise 0 plus Envelope 0 feed channels 1-3, while Noise 1 plus Envelope 1 feed channels 4-6, so noise mode/clock and envelope shape/speed live together in one Shared Generators block rather than in detached Noise and Envelope destinations. Chip Poly allocates all six tone lanes; the shared noise masks remain group hardware rather than fake seventh/eighth note lanes.
- Atari POKEY: Sources are channels 1-4 in a 2x2 pair/filter matrix. Pairing 1+2 or 3+4 consumes the second channel as a 16-bit AUDF high byte and reduces note allocation; high-pass routing is shown as 3 -> 1 and 4 -> 2. Shared AUDC texture/AUDV base controls remain shared, while each card owns only its enable and honest post-AUDV trim.
- PC Speaker: The whole instrument is one mono hardware path: PIT channel 2 -> port `0x61` gate/data -> one-bit speaker cone. Its single source card owns enable and modern output trim. Speaker Mode spans the path, with Pulse Width, Pitch Motion, Click Grit, Speaker Level, and the clearly identified Chipper Gate Decay helper immediately below it. Only Clock and Output remain global; there is no channel mixer, Chip Poly, native ADSR, or hidden oscillator bank.
- ZX Spectrum Beeper: The whole instrument is one ULA output path: generated CPU-style toggles -> port `$FE` -> EAR bit 4 and MIC bit 3 -> one-bit beeper. Its single source card owns enable and modern trim. Beeper Mode spans the path, with Duty + Border, Pitch Motion, MIC Grit, Beeper Level, and the clearly identified Chipper Gate Decay helper immediately below it. The UI identifies border bits 2-0 as metadata and duty as a Chipper-generated timing color rather than inventing a native duty register. Only Clock and Output remain global; there is no Chip Poly, AY surface, native ADSR, or hidden oscillator bank.
- YM2612: six FM source cards share one four-operator patch and operator matrix; channel 6 can become the native DAC stream.
- OPL2/OPL3: nine persistent lane cards change role through `OPL Topology`; the shared two-operator patch and Pair/Mod/Car register state remain visible beside them.

Authentic mode should expose chip-native behavior. Hybrid mode can add musical helpers. Inspired mode should simplify controls and clearly avoid accuracy claims. The requested Strictness selector is a user preference, not a proof badge; the stable host/MIDI parameter remains named `Behavior Strictness` for automation clarity. Each chip descriptor also carries a verification disclosure with a badge, evidence text, known gaps, and explicit `hardwareValidated` / `cycleAccurate` booleans. The footer/status tooltip and renderer descriptor JSON must use that disclosure so a user can request Authentic behavior while still seeing "Verified partial" or "Unverified planned" when that is the honest implementation state, without turning the header into an accuracy warning banner.

SID Osc Interaction sits directly below those cards and writes sync/ring bits for follower voices while the debug renderer reports the resolved bitfield. SID Model sits in Filter + SID Model and reports the resolved 6581/8580 model number plus variant filter/output coefficients in renderer JSON; this remains a partial profile, not a hardware-validated analog model. The same block exposes cutoff, resonance, `$D418` LP/BP/HP/off and combined mode-bit outputs, and `$D417` voice filter routing; external input routing and hardware-calibrated analog response remain future SID filter work.

DMG Stereo Route is the first output-module chip-register selector: it writes `NR51` directly and has renderer coverage for left, right, and split routing. SID, YM2149, SN76489, SAA1099, PC Speaker, and ZX Spectrum Beeper also expose their native source cards in the same source surface, with renderer coverage for source flags and register state; the editor now keeps each source level trim visibly paired with its channel card and CC tooltip. PSG cores expose Stereo Spread as an Output-module modern convenience with renderer debug coverage, while zero spread remains the authentic mono baseline for mono chips and centered stereo for SAA1099; SID reuses the same stable CC93/APVTS role as a chip-specific resonance control instead. SN76489 debug JSON reports whether tone channels are in the period 0/1 constant-output edge case, whether noise is clocked from Tone 3, the resolved divider, and register-origin noise resets, so raw PSG timer/latch behavior is backed by a visible register contract. SAA1099 debug JSON reports frequency/octave registers, left/right amplitude nibbles, mixer tone/noise masks, dual noise controls, envelope group controls, source enables, and Chip Poly assignment. PC Speaker debug JSON reports PIT divisor/frequency, Speaker Mode, port `0x61` gate/data bits, source enable/level, and the absence of Chip Poly. ZX Spectrum Beeper debug JSON reports ULA port `0xFE`, Beeper Mode, EAR/MIC/border bits, source enable/level, and the absence of Chip Poly. YM2149 now exposes envelope shape, envelope speed, global tone/noise mix, and A/B/C mixer overrides as register-backed controls while keeping those controls in compact module surfaces so the UI remains readable. Current live labels, tooltips, readouts, register controls, verification badges, and factory preset dropdown are based on shared catalog/descriptor data and `PatchConfig`; the renderer also seeds unspecified controls from the selected preset recipe or applies a named factory preset so CLI renders match the VST behavior, and it exports descriptor metadata in debug JSON for UI/engine contract tests.

The ymfm-backed FM UI exposes operator register lanes for YM2612/OPN2, YM2151/OPM, and OPL2/OPL3. These lanes show the preset-resolved operator values already written to the engine, such as algorithm/connection context, multiplier, total level, OPL waveform, feedback, and envelope register bytes. YM2612/OPN2 and YM2151/OPM additionally mark each four-op lane as carrier or modulator from the resolved algorithm, so musicians can see which operators reach output. OPN2/OPM provide stable APVTS/MIDI/preset-backed OP1-OP4 Level, Multiplier, Attack, Decay, Sustain Rate, and Release Rate overrides. The YM2612 surface states that this operator patch is shared across all six channels and keeps patch-level Operator Tone/FM Level controls beside the Algorithm and Feedback block.

Future UI work should keep expanding `ChipDescriptor` into richer module, parameter, and layout specs. Small chip-specific editor branches are acceptable as temporary scaffolding when they prove a layout template that should later become data-driven.
